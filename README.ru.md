**Omega-deep** выполняет всё, что делает `omega-check` для одной цели (сканирование портов, идентификация сервисов, ролей, WAF и TLS), и добавляет **обнаружение дополнительных целей** по признакам, оставленным уже просканированной целью (заголовки, перенаправления, сертификат, HTML-ссылки). Обнаружение ограничивается строгими **ограничителями**, а перед сканированием любой обнаруженной цели требуется **явное подтверждение пользователя**. Затем инструмент **восстанавливает граф архитектуры**: кто с кем взаимодействует и с каким уровнем доверия. Это пятый инструмент набора `omega-` (после `omega-fire`, `omega-stress`, `omega-scan` и `omega-check`), организованный по принципам Clean Architecture — полное техническое описание см. в `docs/ARCHITECTURE.md`.

## 1. Назначение и границы

Omega-deep отвечает на вопрос, который не задаёт omega-check: *что ещё находится за этим IP-адресом?* Reverse-прокси, объявляющий свой backend, сертификат, охватывающий несколько хостов, или страница со ссылкой на соседний сервис — это признаки, которые omega-deep осторожно отслеживает, но никогда не использует для автоматического сканирования.

### Что делает Omega-deep

- Сканирует корневую цель так же, как omega-check (системный или сохранённый пользовательский профиль).
- Обнаруживает кандидатов на основе признаков каждого уже просканированного хоста: HTTP-заголовков (`X-Forwarded-Host`, `X-Real-IP`, `X-Backend-Server`, `Via`), перенаправления (`Location`), TLS-сертификата (SAN) и HTML-ссылок — см. [§4](#4-обнаружение-целей-и-ограничители).
- **Никогда** не сканирует обнаруженную цель без явного подтверждения, отдельно для каждой цели: молчание не считается согласием.
- Ограничивает обнаружение строгими правилами: максимальной глубиной, максимальным количеством дополнительных целей и разрешённой подсетью (по умолчанию тот же приватный диапазон, что и у корневой цели).
- Восстанавливает **граф архитектуры** по происхождению каждой принятой цели (`proxy_to`, `redirect_to`, `linked_to`) с уровнем доверия для каждого отношения — см. [§8](#8-граф-архитектуры).
- Показывает результат в TUI (Textual) или в скриптуемом CLI и поддерживает те же три формата экспорта, что и omega-check (JSON, текст и HTML с 5 темами). В HTML граф представлен **настоящей диаграммой**, а не таблицей.
- Присваивает каждой собранной характеристике (сервису и обнаружению) явный уровень доверия — см. [§9](#9-политика-доверия).
- Хранит постоянную историю анализов, которую можно повторно запускать и сравнивать во времени.

### Чего Omega-deep не делает

- Не выполняет активное сканирование уязвимостей, SQLi, XSS или RCE.
- Не сканирует CVE.
- Не определяет операционную систему.
- Не использует низкоуровневые методы сканирования наподобие nmap (SYN-сканирование, сырые пакеты) — только прикладные TCP-соединения.
- Не является инструментом bruteforce или fuzzing.
- Не сканирует обнаруженную цель без явного подтверждения пользователя — ни в одном режиме.
- Не выходит за пределы приватной подсети исходной цели без явной настройки (`--subnet`).
- Не предоставляет веб-панель.

## 2. Установка

### Требования

- Python 3.10+
- Подключение к Интернету для установки зависимостей

### Установка

```bash
[ -d omega-deep ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-deep.tar.gz
cd omega-deep/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если оно ещё не существует.
2. Устанавливает зависимости (`vendor/omega-lib/`, затем `pip install -e .`; единственным источником истины остаётся `pyproject.toml`).
3. Делает `omega-deep.sh` и `install.sh` исполняемыми.
4. Добавляет алиас `deep` в `~/.bashrc` и `~/.zshrc`, не создавая дубликат.

### Зависимости

Указаны в `pyproject.toml` (файл `requirements.txt` больше не используется):
- `omega-lib`: общая библиотека набора (`ConfidenceLevel`, темы, определение терминала), поставляемая в `vendor/omega-lib/`.
- `textual`: TUI, темы и автоматическая адаптация к терминалу.
- `httpx`: HTTP/HTTPS-пробы для сервисов и обнаружения.
- `cryptography`: чтение согласованного TLS-сертификата.
- `jinja2`: шаблоны для HTML-экспорта.
- Зависимости разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `trustme`, `ruff`, `mypy`, `import-linter`.

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для ежедневной работы — запускается без аргументов:

```bash
./omega-deep.sh
```

Если алиас создан, достаточно выполнить в терминале:

```bash
deep
```

Сценарий работы: стартовый экран (закрывается клавишей или щелчком) → главное меню (Анализ / Профили / История / Настройки / Справка) → ввод корневой цели, выбор профиля и ограничителей обнаружения (максимальная глубина, максимальное количество целей, разрешённая подсеть) → анализ (индикатор неопределённого прогресса и отображение сетевых операций в реальном времени) → для каждой партии обнаруженных целей экран подтверждения (одна строка на цель, источник/доверие/доказательство отображаются, переключатель принять/отклонить; по умолчанию ничего не выбрано) → подробности анализа (хосты, порты/сервисы/роли, граф, экспорт) → история, сравнение, повторный запуск и настройки из главного меню. Адаптация к терминалу (цвета, размер, структурное упрощение) выполняется автоматически.

#### Горячие клавиши

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Перемещение между элементами экрана |
| `Tab` / `Shift+Tab` | Перемещение между полями формы |
| `Esc` | Возврат к предыдущему экрану (на стартовом экране запрашивается подтверждение выхода) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить определение терминала |
| `a` | Показать справку |
| `q` | Выйти с подтверждением |

### Скриптуемый режим (CLI)

Любая подкоманда запускает режим CLI:

```bash
# Анализ цели (сканирование корневой цели + обнаружение нескольких целей)
./omega-deep.sh analyze 192.168.1.10 --profile web --max-depth 3 --max-targets 10 --subnet 192.168.1.0/24

# История (фильтрация по корневой цели)
./omega-deep.sh history --target 192.168.1.10 --limit 20

# Подробности анализа (текст, JSON или HTML) — на выбор 5 тем экспорта
./omega-deep.sh show <scan_id> --format html --theme omega-base --output rapport.html

# Сравнение двух анализов (состояние портов корневой цели)
./omega-deep.sh compare <scan_id_a> <scan_id_b>

# Пользовательские профили портов
./omega-deep.sh profile list
./omega-deep.sh profile create labo --ports 22,80,443 --description "Мой профиль"
./omega-deep.sh profile edit labo --ports 22,80,443,8080
./omega-deep.sh profile pin labo
./omega-deep.sh profile unpin labo
./omega-deep.sh profile delete labo
```

В CLI подтверждение обнаруженных целей выполняется отдельным интерактивным вопросом (`Сканировать <цель>? [д/Н]`), при этом перед вопросом отображается доказательство. `--auto-validate` принимает всё без проверки (**не рекомендуется**, выводится предупреждение). В неинтерактивной среде (без TTY и без `--auto-validate`) любая обнаруженная цель по умолчанию отклоняется, а не сканируется без подтверждения.

### Допустимые форматы целей

```text
192.168.1.10                IPv4
example.org                 Имя хоста
http://example.org          URL HTTP (схема удаляется перед разрешением)
https://example.org:8443    URL HTTPS с портом (схема и порт удаляются)
```

Перед DNS-разрешением возможные схема и порт удаляются (`domain/targets/validation.py::normalize_target_input`): можно вставить полный URL, будет сохранён только хост. Обнаруженные цели нормализуются таким же образом, но никогда не сканируются без подтверждения (см. [§4](#4-обнаружение-целей-и-ограничители)).

## 4. Обнаружение целей и ограничители

### Источники признаков

| Источник | Происхождение | Доверие |
|---|---|---|
| `header` | `X-Forwarded-Host`, `X-Real-IP`, `X-Backend-Server`, `Via` | `DECLARED` |
| `redirection` | Заголовок `Location` HTTP-ответа | `DECLARED` |
| `certificate` | SAN (Subject Alternative Names) согласованного TLS-сертификата | `DECLARED` |
| `html_link` | Ссылки (`<a href>`), предоставленные страницей | `INFERRED` |

Значение `DECLARED` остаётся самодекларацией цели и может быть подделано — см. [§10](#10-защита-от-подделанных-значений). `html_link` намеренно является самым слабым источником: простая ссылка не заявляет об инфраструктурном отношении.

### Ограничители (всегда активны и не отключаются)

- **Область**: кандидат должен быть приватным IP в том же `/24`, что и корневая цель, если не указан `--subnet`. При явном `--subnet` учитывается только принадлежность заданной подсети, даже если она включает публичные IP: исключение разрешает именно явная настройка. Неразрешённое имя хоста никогда не принимается этим фильтром.
- **Глубина**: `--max-depth` (по умолчанию 3) — максимум A → B → C → D.
- **Количество целей**: `--max-targets` (по умолчанию 10) — суммарно для всех уровней.

### Подтверждение (никакого сканирования без согласия)

Каждая предложенная цель проходит состояния `PROPOSED → PRESENTED → ACCEPTED` или `REJECTED`. Правило **fail-safe** означает: цель, которая не была явно принята (молчание, закрытие экрана, прерывание, тайм-аут или отсутствие TTY), считается отклонённой — никогда наоборот. В TUI отдельный экран показывает цели партии, доказательство и доверие; для каждой строки можно принять или отклонить цель, принять или отклонить всё, а клавиша Esc по умолчанию отклоняет всё. В CLI задаётся вопрос для каждой цели; `--auto-validate` (не рекомендуется) — единственный способ обойти интерактивность.

## 5. Профили сканирования

| Профиль | Описание | Закреплён |
|---|---|---|
| `minimal` | Очень быстрое сканирование: SSH + HTTP + HTTPS (22, 80, 443) | да |
| `classic` | Классические сервисы Интернета/LAN | да |
| `web` | Веб-сервисы и альтернативные порты | нет |
| `db` | Базы данных и сервисы данных | нет |
| `remote` | Удалённый доступ: shell, рабочий стол, RustDesk | нет |
| `mail` | Почтовые сервисы | нет |
| `dns` | DNS-сервисы | нет |
| `iot` | IoT-устройства, камеры, маршрутизаторы и умный дом | нет |
| `dev` | Среды разработки и лаборатории | нет |
| `docker` | Docker, Swarm и распространённые контейнерные сервисы | нет |
| `complet` | **Генерируется на лету**: отсортированное объединение без дубликатов всех профилей выше | нет |
| *пользовательский профиль* | Создаётся на экране **Профили** (TUI) или через `profile create` (CLI), отображается вместе с системными профилями и имеет префикс `* ` в TUI | нет |

Профиль применяется к корневой цели **и** к каждой принятой обнаруженной цели — отдельный профиль для каждого хоста не используется. Полное описание, правила проверки и управление пользовательскими профилями: `docs/PROFILES.md`.

## 6. Архитектура

Omega-deep организован по принципам **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins / shared), соответствует шаблону набора `omega-` (см. `omega-scan`/`omega-check`) и проверяется `import-linter` при каждом изменении. Полное описание находится в **`docs/ARCHITECTURE.md`**.

Краткий обзор:

```text
src/omega_deep/
├── domain/          Чистая бизнес-логика: сканирование, цели, сервисы, профили,
│                    отчёты, discovery (предложенные цели, конечный автомат
│                    подтверждения), architecture (граф, правила отношений)
├── application/     Сценарии использования (commands/queries), включая
│                    discover_targets, validate_targets, reconstruct_architecture
│                    (новые по сравнению с omega-check)
├── ports/           Контракты приложения (probers, включая discovery_prober,
│                    repositories, exporters...)
├── infrastructure/  Конкретные реализации (socket/httpx/cryptography, SQLite,
│                    SVG-рендеринг графа; Textual находится НЕ здесь)
├── interfaces/      tui/ (Textual) и cli/ (скриптуемый), со строгим равенством функций
├── app/             Сборка (DependencyContainer, bootstrap, жизненный цикл)
├── core/, shared/   Общая терминология и утилиты, не относящиеся к бизнес-логике
└── plugins/         Подготовленная пустая структура (подтверждённых расширений нет)
```

Правила проектирования:
- `domain/services/policies.py`: классифицирует уже собранные признаки и никогда не выполняет сетевые операции.
- `domain/discovery/policies.py`: ограничители области, глубины и количества; чистая логика, тестируемая без сети.
- `domain/architecture/service.py`: восстанавливает граф по происхождению, уже записанному в каждом `Host`, и не выполняет новых запросов.
- `infrastructure/network/` и `infrastructure/discovery/`: выполняют сетевые операции (sockets, `httpx`, `cryptography`), но ничего не оценивают.
- `interfaces/`: только отображают данные и не содержат бизнес-логики. Экран подтверждения вызывает `validate_targets`, но не реализует правило fail-safe самостоятельно.
- `infrastructure/exporters/`: читают результат анализа (сканирование, хосты, граф) и ничего не пересчитывают.

## 7. Идентификация сервисов и ролей

### Обнаруживаемые протоколы

| Протокол | Проба | Собираемые данные |
|---|---|---|
| HTTP / HTTPS | `httpx` | Баннер `Server`, заголовки аутентификации |
| TLS | `cryptography` (согласованный сертификат, включая `CERT_NONE`) | Версия, cipher, subject/issuer сертификата |
| SSH | Необработанный баннер | ПО и версия (например, `OpenSSH 10.4`) |
| VNC (RFB) | Коды безопасности, объявленные сервером | Поддерживаемые типы аутентификации |
| Общий | Необработанный баннер открытого нераспознанного порта | Осторожное извлечение без агрессивной эвристики |

### Выводимые роли

Роли выводятся из **реально согласованного протокола**, а не из предположительного номера порта:

| Роль | Условие | Доверие |
|---|---|---|
| `веб-сервер` | Подтверждён протокол HTTP/HTTPS | `INFERRED` |
| `shell-доступ` | Подтверждён протокол SSH | `CORROBORATED` |
| `графический доступ` | Подтверждён протокол VNC | `CORROBORATED` |
| `база данных` | Порт входит в диапазон системного профиля `db` | `INFERRED` |

### Известные сигнатуры WAF

Определяются по декларативным заголовкам (`server`, `x-sdk`). Наличие **заявляется самой целью** и не проверяется независимо: Cloudflare, Sucuri, Akamai, Imperva Incapsula, AWS ELB (приведён справочно и не является прикладным WAF в строгом смысле).

## 8. Граф архитектуры

Граф восстанавливается только по происхождению, уже записанному в каждом принятом хосте (`discovered_from`/`discovery_source`/`discovery_confidence`): новые сетевые запросы не выполняются, исходные признаки повторно не анализируются.

### Создаваемые отношения

| Отношение | Источник обнаружения | Значение |
|---|---|---|
| `proxy_to` | `header` | Корневая цель или уже принятый хост, вероятно, является прокси к обнаруженной цели |
| `redirect_to` | `redirection` | Наблюдалось HTTP-перенаправление к обнаруженной цели |
| `linked_to` | `certificate` или `html_link` | Наиболее нейтральное отношение: общая инфраструктура/приложение без утверждения направления потока |

`backend_of` (обратное ребро `proxy_to`) намеренно не создаётся: это дублирование, а не новое умозаключение.

### Отображение

- **TUI** (подробности анализа) и **экспорты JSON/текста**: список рёбер (источник, отношение, цель, доверие); терминал не предназначен для сложной графики.
- **HTML-экспорт**: **настоящая SVG-диаграмма** (узлы — круги, рёбра — подписанные стрелки), многоуровневая раскладка от корневой цели, размер пропорционален количеству обнаруженных машин. Тяжёлые библиотеки раскладки не требуются: граф по построению мал и ограничен правилами [§4](#4-обнаружение-целей-и-ограничители).

## 9. Политика доверия

Каждое собранное поле получает один из уровней:

| Уровень | Значение |
|---|---|
| `VERIFIED` | Непосредственно наблюдаемый протокольный факт, который цель не может подделать (например, закрытый порт, подтверждённый TCP RST, или фактически согласованная версия TLS). |
| `DECLARED` | Значение, самостоятельно объявленное целью в полностью контролируемом ею поле (например, баннер `Server` или заголовок `X-Backend-Server`): правдоподобно, но легко подделывается. |
| `CORROBORATED` | Значение `DECLARED`, подтверждённое независимым признаком (например, роль SSH после фактического согласования протокола). |
| `INFERRED` | Вывод из шаблона или эвристики без явного объявления цели (например, HTML-ссылка). |
| `UNKNOWN` | Полезных признаков нет или цель активно скрывает их. |

## 10. Защита от подделанных значений

Omega-deep не доверяет автоматически данным, объявленным самой целью, и явно сообщает об этом. Обнаружение целей особенно чувствительно: вредоносная цель *может* объявить ложный `X-Backend-Server`, чтобы направить обнаружение на выбранный IP-адрес. Используются две независимые структурные защиты:
- Производная от цели информация никогда не получает уровень `VERIFIED` только потому, что была объявлена: баннер `Server` или заголовок `X-Backend-Server` остаётся `DECLARED`, какой бы правдоподобной ни была его величина.
- Ограничитель области ([§4](#4-обнаружение-целей-и-ограничители)) ограничивает направление объявленной цели (тот же приватный `/24`, если явно не задана другая подсеть), а подтверждение пользователя определяет, будет ли она вообще просканирована. Ложная цель вне области даже не предлагается; цель внутри области всё равно требует явного подтверждения.

## 11. Совместимость с терминалами

TUI (Textual) автоматически определяет возможности терминала (эмулятор и размер) и соответственно адаптирует структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`) без ручных флагов. CLI всегда использует обычный текст и не зависит от терминала. Политика общая для всего набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| Linux TTY, legacy SSH | `mono` |
| Неизвестный эмулятор | `reduced` (значение по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Максимальный профиль |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **наиболее ограничительный из двух** (эмулятор и размер). Ghostty в полноэкранном режиме, уменьшенный до 70 столбцов, перейдёт в `mono`, даже если сам эмулятор допускает `complete`. Профиль можно обновить на лету клавишей `r`.

## 12. Экспорт

По умолчанию отчёты создаются в `var/exports/` (путь выполнения привязан к каталогу проекта; для переопределения используется `$OMEGA_DEEP_VAR_DIR`) или по указанному пути (`--output` в CLI, диалог в TUI). Имя файла содержит тип и время: `analyse-{profil}-{date}.ext`, а для пользовательского профиля — `analyse-custom-{date}.ext`.

### JSON — источник истины

Полная структура анализа (`Scan` + `Host[]` + `ArchitectureGraph`) в строгом JSON-совместимом формате с уровнями доверия.

### Текст — компактный отчёт для человека

Читается вне терминала, без ANSI-кодов; граф представлен списком рёбер.

### HTML — автономный веб-отчёт

Доступно 5 тем (`--theme` в CLI или селектор в TUI; по умолчанию используется активная тема интерфейса, если существует соответствующий вариант). Специализированная компоновка: контейнер, информационная сетка, статистические блоки по состояниям портов, цветные бейджи и **SVG-диаграмма графа архитектуры** (см. [§8](#8-граф-архитектуры)), в том же визуальном стиле, что и `omega-scan`/`omega-check`.

## 13. История и сравнение

Каждый анализ сохраняется в SQLite (`var/db/omega-deep.db`): `scan_id` содержит корневую цель, все обнаруженные и принятые хосты, а также восстановленный граф. Историю можно просматривать по корневой цели, включая отдельное количество обнаруженных целей; доступны подробности прошлого анализа (хосты и граф), сравнение двух анализов (только состояние портов **корневой цели** — сравнение графов обнаружения пока не требуется) и повторный запуск анализа той же корневой цели без повторного ввода.
