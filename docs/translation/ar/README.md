**Omega-deep** يؤدي كل ما يؤديه `omega-check` على هدف واحد (فحص المنافذ، والتعرّف على الخدمات، والأدوار، وWAF، وTLS)، ويضيف إليه **اكتشاف أهداف إضافية** انطلاقًا من القرائن التي يتركها الهدف المفحوص مسبقًا (الترويسات، وعمليات إعادة التوجيه، والشهادة، وروابط HTML)، ضمن **حدود أمان صارمة** ومع **تأكيد صريح من المستخدم** قبل فحص أي هدف مكتشَف، ثم **يعيد بناء مخطط للبنية** (من يتواصل مع من، وبأي درجة ثقة). هي إحدى أدوات مجموعة `omega-`، مبنية وفق Clean Architecture — انظر `docs/ARCHITECTURE.md` لكل التفاصيل التقنية.

## 1. الرؤية والنطاق

يجيب Omega-deep عن سؤال لا يطرحه omega-check: *ماذا يوجد أيضًا خلف هذا العنوان IP؟* وكيل عكسي يعلن عن خادمه الخلفي، وشهادة تغطي عدة مضيفين، وصفحة تشير إلى خدمة مجاورة — كلها قرائن يتتبّعها omega-deep بحذر، ولا يتصرف بمفرده أبدًا.

### ما يفعله Omega-deep

- يفحص هدفًا جذريًا تمامًا كما يفعل omega-check (ملف تعريف النظام، أو ملف تعريف شخصي محفوظ).
- يكتشف أهدافًا مرشّحة من القرائن التي يتركها كل مضيف مفحوص مسبقًا: ترويسات HTTP ‏(`X-Forwarded-Host` و`X-Real-IP` و`X-Backend-Server` و`Via`)، وإعادة التوجيه (`Location`)، وشهادة TLS ‏(SAN)، وروابط HTML — انظر [§4](#4-اكتشاف-الأهداف-وحدود-الأمان).
- **لا** يفحص **أبدًا** هدفًا مكتشَفًا دون تأكيد صريح، هدفًا تلو الآخر — الصمت لا يعني القبول أبدًا.
- يقيّد الاكتشاف بحدود أمان صارمة: أقصى عمق، وأقصى عدد من الأهداف الإضافية، والشبكة الفرعية المسموح بها (افتراضيًا النطاق الخاص نفسه للهدف الجذري).
- يعيد بناء **مخطط البنية** من مصدر كل هدف مقبول (`proxy_to` و`redirect_to` و`linked_to`)، مع مستوى ثقة لكل علاقة — انظر [§8](#8-مخطط-البنية).
- يعرض النتيجة في TUI (Textual) أو في CLI قابل للبرمجة النصية، مع أنواع التصدير الثلاثة نفسها في omega-check ‏(JSON، ونص، وHTML بخمس سمات) — والمخطط هناك **رسم بياني مرسوم فعلًا** بلغة HTML، لا جدول.
- يمنح كل معلومة مجمّعة (خدمةً كانت أو اكتشافًا) مستوى ثقة صريحًا — انظر [§9](#9-سياسة-الثقة).
- يحتفظ بسجل دائم للتحليلات، قابل لإعادة التشغيل والمقارنة عبر الزمن.

### ما لا يفعله Omega-deep

- فحص الثغرات النشط: لا SQLi ولا XSS ولا RCE.
- فحص CVE.
- التعرّف على نظام التشغيل.
- تقنيات الفحص منخفضة المستوى على طريقة nmap (فحص SYN، والحزم الخام) — اتصال TCP على مستوى التطبيق فقط.
- أداة للتخمين بالقوة الغاشمة أو للتشويش (fuzzing).
- فحص هدف مكتشَف دون تأكيد صريح من المستخدم — أبدًا، في أي وضع.
- الاكتشاف خارج الشبكة الفرعية الخاصة بالهدف الأولي، ما لم يُضبط ذلك صراحةً (`--subnet`).
- لوحة تحكم ويب.

## 2. التثبيت

### المتطلبات

- Python 3.10+
- اتصال بالإنترنت، من أجل الاعتماديات

### التثبيت

```bash
[ -d omega-deep ] && echo "ℹ️ مُستخرَج هنا مسبقًا، تم تخطي الخطوة." || tar -xzf omega-deep.tar.gz
cd omega-deep/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. ينشئ البيئة الافتراضية `.venv` إن لم تكن موجودة.
2. يثبّت الاعتماديات (`vendor/omega-lib/` ثم `pip install -e .`؛ ويبقى `pyproject.toml` المرجع الوحيد).
3. يجعل `omega-deep.sh` و`install.sh` قابلين للتنفيذ.
4. يضيف الاسم المستعار `deep` إلى `~/.bashrc` و`~/.zshrc` (من دون تكرار إن كان موجودًا).

### الاعتماديات

مُعرَّفة في `pyproject.toml` (لم يعد هناك `requirements.txt`):
- `omega-lib`: المكتبة المشتركة للمجموعة (`ConfidenceLevel`، والسمات، واكتشاف الطرفية) — مضمّنة في `vendor/omega-lib/`
- `textual`: واجهة TUI، والسمات، والتكيّف التلقائي مع الطرفية
- `httpx`: مسابير HTTP/HTTPS (للخدمة وللاكتشاف)
- `cryptography`: قراءة شهادة TLS المتفاوض عليها
- `jinja2`: قوالب تصدير HTML
- اعتماديات التطوير (`pip install -e ".[dev]"`): `pytest` و`pytest-asyncio` و`pytest-cov` و`pytest-httpserver` و`trustme` و`ruff` و`mypy` و`import-linter`

## 3. الاستخدام

### الوضع التفاعلي (TUI)

يُنصح به للاستخدام اليومي — يُشغَّل من دون وسائط:

```bash
./omega-deep.sh
```
إن أنشأت الاسم المستعار، فاكتب `deep` فقط في الطرفية:
```bash
deep
```

المسار: شاشة البداية (تُغلق بضغطة مفتاح أو نقرة) ← القائمة الرئيسية (تحليل / ملفات التعريف / السجل / الإعدادات / مساعدة) ← إدخال الهدف الجذري، واختيار ملف التعريف وحدود أمان الاكتشاف (أقصى عمق، وأقصى عدد من الأهداف، والشبكة الفرعية المسموح بها) ← التحليل (مؤشر تقدّم غير محدد وسجل مباشر لعمليات الشبكة) ← عند كل دفعة من الأهداف المكتشفة، شاشة تأكيد (سطر لكل هدف، مع عرض المصدر/الثقة/الدليل، ومفتاح قبول/رفض — لا شيء محدد افتراضيًا) ← تفاصيل التحليل (المضيفون، والمنافذ/الخدمات/الأدوار، والمخطط، والتصدير) ← السجل/المقارنة/إعادة التشغيل والإعدادات من القائمة الرئيسية. التكيّف مع الطرفية (الألوان، والحجم، وتبسيط البنية) تلقائي.

#### اختصارات لوحة المفاتيح

| المفتاح | الإجراء |
|---|---|
| `↑` / `↓` | التنقل بين عناصر الشاشة |
| `Tab` / `Shift+Tab` | التنقل بين حقول النموذج |
| `Esc` | العودة إلى الشاشة السابقة (تأكيد الخروج في الشاشة الرئيسية) |
| `t` | السمة التالية (تُطبَّق فورًا دون تأكيد) |
| `r` | تحديث اكتشاف الطرفية |
| `a` | عرض المساعدة |
| `q` | الخروج (مع تأكيد) |

### لغات الواجهة

الواجهة متاحة بـ 17 لغة: الفرنسية، والإنجليزية، والإسبانية، والبرتغالية (البرازيل)، والإيطالية، والألمانية، والهولندية، والبولندية، والروسية، والصينية المبسّطة، والفيتنامية، والتايلاندية، والإندونيسية، واليابانية، والكورية، والهندية، والعربية. يتم الاختيار من الإعدادات («Langue / Language») ويسري بعد إعادة تشغيل الواجهة؛ ويفرض المتغير `OMEGA_DEEP_LANG` (مثلًا `OMEGA_DEEP_LANG=ar ./omega-deep.sh`) لغة طوال جلسة واحدة. عند التشغيل من omega-suite، يأخذ omega-deep لغة المجموعة. على وحدة التحكم النصية في Linux ‏(TTY)، تُعرض اللغات ذات الكتابة غير اللاتينية بالإنجليزية طوال الجلسة. يبقى سطر الأوامر بالفرنسية.

### التواصل والدعم

تتيح المساعدة (المفتاح `a`) شاشة **التواصل والدعم**: *ادفع ثمن قهوة* (صفحة PayPal الخاصة بالمطوّر)، و*التواصل مع الدعم* (عنوان البريد الإلكتروني ونموذج التواصل في الموقع، معروضان بوضوح)، و*تسجيلي كمستخدم (مجهول الهوية)* و*التحقق من التحديثات*. التسجيل اختياري، ومعطّل افتراضيًا، ويُرسل مرة واحدة فقط: يُستخدم فقط لإحصاء المستخدمين، وإن رغبت، قارتهم أو بلدهم (قوائم مغلقة، دون أي نص حر). يُرسل مفتاحًا مولَّدًا عشوائيًا واسم البرنامج (`omega-deep`) وإصداره؛ ولا يُرسل أبدًا اسمًا أو اسم جهاز أو إعدادًا أو هدفًا أو نتيجة. لا يُحفظ عنوان IP في التسجيلات، لكنه، كأي زيارة، يمر عبر فحوص الأمان وسجل الخادم المستقبِل. يمكن السحب في أي وقت من الشاشة نفسها (*إلغاء تسجيلي*). يقرأ التحقق من التحديثات قائمة الإصدارات المنشورة على الموقع فقط، ولا يحدث أبدًا دون نقرة.

### وضع البرمجة النصية (CLI)

أي أمر فرعي يفعّل وضع CLI:

```bash
# تحليل هدف (فحص الهدف الجذري + اكتشاف أهداف متعددة)
./omega-deep.sh analyze 192.168.1.10 --profile web --max-depth 3 --max-targets 10 --subnet 192.168.1.0/24

# السجل (قابل للتصفية حسب الهدف الجذري)
./omega-deep.sh history --target 192.168.1.10 --limit 20

# تفاصيل تحليل (نص أو JSON أو HTML) — اختيار من 5 سمات للتصدير
./omega-deep.sh show <scan_id> --format html --theme omega-base --output report.html

# مقارنة تحليلين (حالة منافذ الهدف الجذري)
./omega-deep.sh compare <scan_id_a> <scan_id_b>

# ملفات تعريف المنافذ الشخصية
./omega-deep.sh profile list
./omega-deep.sh profile create lab --ports 22,80,443 --description "ملفي الشخصي"
./omega-deep.sh profile edit lab --ports 22,80,443,8080
./omega-deep.sh profile pin lab
./omega-deep.sh profile unpin lab
./omega-deep.sh profile delete lab
```

في CLI، يجري تأكيد الأهداف المكتشفة عبر سؤال تفاعلي لكل هدف (`Scanner <cible> ? [o/N]`، بالفرنسية كبقية سطر الأوامر)، مع عرض تفاصيل الدليل قبل كل سؤال. يقبل `--auto-validate` كل شيء دون مراجعة (**غير مستحسن**، ويُعرض تحذير)؛ وفي بيئة غير تفاعلية (لا TTY ولا `--auto-validate`) يُرفض كل هدف مكتشَف افتراضيًا بدلًا من فحصه دون تأكيد.

### صيغ الهدف المقبولة

```text
192.168.1.10                IPv4
example.org                 اسم المضيف
http://example.org          عنوان HTTP  (يُزال المخطط قبل التحليل)
https://example.org:8443    عنوان HTTPS مع منفذ  (يُزال المخطط والمنفذ)
```

يُزال المخطط والمنفذ، إن وُجدا، قبل تحليل DNS ‏(`domain/targets/validation.py::normalize_target_input`) — لصق عنوان URL كامل يعمل، ولا يُحتفظ إلا بالمضيف. أما الأهداف *المكتشَفة* فتُوحَّد صيغتها بالطريقة نفسها، لكنها لا تُفحص أبدًا دون تأكيد (انظر [§4](#4-اكتشاف-الأهداف-وحدود-الأمان)).

## 4. اكتشاف الأهداف وحدود الأمان

### مصادر القرائن

| المصدر | المنشأ | الثقة |
|---|---|---|
| `header` | `X-Forwarded-Host` و`X-Real-IP` و`X-Backend-Server` و`Via` | `DECLARED` |
| `redirection` | ترويسة `Location` في استجابة HTTP | `DECLARED` |
| `certificate` | SAN ‏(Subject Alternative Names) في شهادة TLS المتفاوض عليها | `DECLARED` |
| `html_link` | الروابط (`<a href>`) التي تقدّمها الصفحة | `INFERRED` |

تبقى القيمة `DECLARED` تصريحًا ذاتيًا من الهدف (قابلًا للتزوير) — انظر [§10](#10-الحماية-من-القيم-المزوّرة). وقد جُعل `html_link` عمدًا أضعف المصادر: فمجرد رابط لا يعلن أي علاقة على مستوى البنية التحتية.

### حدود الأمان (مفعّلة دائمًا، لا يمكن تعطيلها)

- **المحيط**: يجب أن يكون الهدف المرشّح عنوان IP خاصًا ضمن `/24` نفسه الخاص بالهدف الجذري، ما لم يُحدَّد `--subnet` صراحةً (وعندها لا يُعتدّ إلا بالانتماء إلى الشبكة الفرعية المحددة، حتى لو شملت عناوين IP عامة — فالضبط الصريح هو ما يسمح بالاستثناء). لا يقبل هذا المرشّح أبدًا اسم مضيف لم يُحلَّل (فتحليله للتحقق منه يُعدّ في حد ذاته إجراءً شبكيًا خارج نطاق هذا التحقق).
- **العمق**: `--max-depth` (الافتراضي 3) — بحد أقصى A ← B ← C ← D.
- **عدد الأهداف**: `--max-targets` (الافتراضي 10) — في جميع الأعماق مجتمعة.

### التأكيد (لا فحص أبدًا دون موافقة)

يمر كل هدف مقترح بـ `PROPOSED → PRESENTED → ACCEPTED` أو `REJECTED`. والقاعدة **آمنة عند الإخفاق**: كل هدف لم يُقبل صراحةً قط (صمت، أو إغلاق الشاشة، أو مقاطعة، أو انتهاء المهلة، أو غياب TTY) يُعامَل كهدف مرفوض — ولا يحدث العكس أبدًا. في TUI، تعرض شاشة مخصصة أهداف الدفعة مع الدليل والثقة، ومفتاح قبول/رفض لكل سطر، و«قبول الكل»/«رفض الكل»، ورفضًا كاملًا افتراضيًا عند الضغط على Esc. وفي CLI، سؤال واحد لكل هدف؛ و`--auto-validate` (غير مستحسن) هو الطريقة الوحيدة لتجاوز التفاعل.

| `docker` | Docker وSwarm والخدمات الشائعة في الحاويات | لا |
| `complet` | **يُنشأ فوريًا**: اتحاد مرتّب وخالٍ من التكرار لكل ملفات التعريف أعلاه | لا |
| *ملف تعريف شخصي* | يُنشأ في شاشة **ملفات التعريف** (TUI) أو بالأمر `profile create` ‏(CLI)، ويُعرض مع ملفات تعريف النظام، مسبوقًا بـ `* ` في TUI | لا |

يُطبَّق ملف التعريف على الهدف الجذري **و**على كل هدف مكتشَف مقبول — لا يوجد ملف تعريف مختلف لكل مضيف. التفاصيل الكاملة، وقواعد التحقق، وإدارة ملفات التعريف الشخصية: `docs/PROFILES.md`.

## 6. البنية المعمارية

بُني Omega-deep وفق **Clean Architecture** ‏(domain / application / infrastructure / interfaces / ports / core / app / plugins / shared)، بما يتّسق مع قالب مجموعة `omega-` (انظر `omega-scan`/`omega-check`)، ويتحقق منها `import-linter` عند كل تعديل. التفاصيل الكاملة في **`docs/ARCHITECTURE.md`**.

نظرة عامة قصيرة جدًا:

```text
src/omega_deep/
├── domain/          منطق أعمال خالص: الفحوص، والأهداف، والخدمات، وملفات التعريف، والتقارير،
│                    discovery (الأهداف المقترحة، وآلة حالات التأكيد)،
│                    architecture (المخطط، وقواعد العلاقات)
├── application/     حالات الاستخدام (commands/queries) — ومنها discover_targets،
│                    validate_targets، reconstruct_architecture (جديدة مقارنة بـ omega-check)
├── ports/           العقود التي يتوقعها التطبيق (المسابير، ومنها discovery_prober،
│                    والمستودعات، والمُصدِّرات...)
├── infrastructure/  تنفيذات فعلية (socket/httpx/cryptography، SQLite،
│                    رسم المخطط بصيغة SVG — Textual ليس هنا)
├── interfaces/      tui/ ‏(Textual) وcli/ (قابل للبرمجة النصية)، بتكافؤ وظيفي صارم
├── app/             التجميع (DependencyContainer، bootstrap، دورة الحياة)
├── core/, shared/   مفردات مشتركة، وأدوات مساعدة خارج منطق الأعمال
└── plugins/         البنية جاهزة، فارغة (لا يوجد محور توسعة مؤكد)
```

قواعد التصميم:
- `domain/services/policies.py`: يصنّف القرائن المجمّعة مسبقًا، ولا يتصل بالشبكة أبدًا.
- `domain/discovery/policies.py`: حدود أمان المحيط/العمق/العدد — منطق خالص قابل للاختبار دون شبكة.
- `domain/architecture/service.py`: يعيد بناء المخطط من المصدر الذي يحمله كل `Host` مسبقًا، ولا يرسل أي طلب جديد.
- `infrastructure/network/` و`infrastructure/discovery/`: يتصلان بالشبكة (المقابس، و`httpx`، و`cryptography`)، ولا يُصدران أحكامًا أبدًا.
- `interfaces/`: تعرض فقط، ولا تحتوي أي منطق أعمال — شاشة تأكيد الأهداف المكتشفة تستدعي `validate_targets`، ولا تطبّق قاعدة الأمان عند الإخفاق بنفسها.
- `infrastructure/exporters/`: تقرأ نتيجة التحليل (الفحص، والمضيفين، والمخطط)، ولا تعيد حساب أي شيء.

## 7. التعرّف على الخدمات والأدوار

### البروتوكولات المكتشفة

| البروتوكول | المسبار | التفاصيل المجمّعة |
|---|---|---|
| HTTP / HTTPS | `httpx` | لافتة `Server`، وترويسات المصادقة |
| TLS | `cryptography` (الشهادة المتفاوض عليها، بما فيها `CERT_NONE`) | الإصدار، والتشفير، وصاحب الشهادة/مُصدِرها |
| SSH | لافتة خام | البرنامج والإصدار (مثل `OpenSSH 10.4`) |
| VNC (RFB) | رموز الأمان التي يعلنها الخادم | أنواع المصادقة المدعومة |
| عام | لافتة خام على منفذ مفتوح غير معروف | استخراج حذر، دون قواعد استدلالية متشددة |

### الأدوار المستنتجة

تُستنتج من البروتوكول **المتفاوض عليه فعلًا**، ولا تُستنتج أبدًا من افتراض مبني على رقم المنفذ:

| الدور | الشرط | الثقة |
|---|---|---|
| `خادم ويب` | تأكيد بروتوكول HTTP/HTTPS | `INFERRED` |
| `وصول إلى الصدفة` | تأكيد بروتوكول SSH | `CORROBORATED` |
| `وصول رسومي` | تأكيد بروتوكول VNC | `CORROBORATED` |
| `قاعدة بيانات` | المنفذ ضمن نطاق ملف تعريف النظام `db` | `INFERRED` |

### تواقيع WAF المعروفة

تُكتشف عبر ترويسة تصريحية (`server`، `x-sdk`) — وجودها **مُعلن من الهدف**، ولا يُتحقق منه بشكل مستقل أبدًا: Cloudflare وSucuri وAkamai وImperva Incapsula وAWS ELB (مُدرج للعلم، وليس جدار حماية تطبيقات بالمعنى الدقيق).

## 8. مخطط البنية

يُعاد بناؤه حصريًا من المصدر الذي يحمله كل مضيف مقبول مسبقًا (`discovered_from`/`discovery_source`/`discovery_confidence`) — دون أي طلب شبكي جديد، ودون إعادة تحليل القرائن الخام.

### العلاقات المُنتَجة

| العلاقة | مصدر الاكتشاف | المعنى |
|---|---|---|
| `proxy_to` | `header` | الهدف الجذري (أو مضيف مقبول مسبقًا) هو على الأرجح وكيل نحو الهدف المكتشَف |
| `redirect_to` | `redirection` | رُصدت إعادة توجيه HTTP نحو الهدف المكتشَف |
| `linked_to` | `certificate` أو `html_link` | العلاقة الأكثر حيادًا — بنية تحتية/تطبيق مشترك، دون الجزم باتجاه التدفق |

لا يُنتَج `backend_of` (الضلع العكسي لـ `proxy_to`) عمدًا — إذ سيكون تكرارًا للمعلومة، لا استنتاجًا جديدًا.

### العرض

- **TUI** (تفاصيل التحليل) و**تصدير JSON/النص**: قائمة الأضلاع (المصدر، والعلاقة، والوجهة، والثقة) — فالطرفية ليست المكان المناسب لعرض رسومي غني.
- **تصدير HTML**: **رسم SVG حقيقي** (العُقد = دوائر، والأضلاع = أسهم موسومة)، بتخطيط طبقي يُحسب انطلاقًا من الهدف الجذري، وحجم يتناسب مع عدد الأجهزة المكتشفة — دون الاعتماد أبدًا على مكتبة ثقيلة لتخطيط المخططات؛ ويبقى المخطط صغيرًا بحكم التصميم (تحدّه حدود الأمان في [§4](#4-اكتشاف-الأهداف-وحدود-الأمان)).

## 9. سياسة الثقة

يحمل كل حقل مجمّع أحد المستويات التالية:

| المستوى | المعنى |
|---|---|
| `VERIFIED` | حقيقة بروتوكولية مُلاحظة مباشرة، لا يستطيع الهدف تزويرها (مثل منفذ مغلق أكّده TCP RST، أو إصدار TLS متفاوض عليه فعلًا). |
| `DECLARED` | قيمة أعلنها الهدف بنفسه في حقل يتحكم فيه بالكامل (مثل لافتة `Server`، أو ترويسة `X-Backend-Server`) — معقولة لكنها قابلة للتزوير كما يشاء. |
| `CORROBORATED` | قيمة `DECLARED` أكّدتها قرينة مستقلة (مثل دور SSH، لأن البروتوكول جرى التفاوض عليه فعلًا). |
| `INFERRED` | مستنتجة من نمط/قاعدة استدلالية، دون تصريح صريح من الهدف (مثل رابط HTML). |
| `UNKNOWN` | لا توجد قرينة صالحة، أو أخفاها الهدف عمدًا. |

## 10. الحماية من القيم المزوّرة

لا يثق Omega-deep بأي بيانات أعلنها الهدف بنفسه دون الإشارة إلى ذلك صراحة — واكتشاف الأهداف هو الجزء الأكثر حساسية في المشروع: فالهدف الخبيث *قد* يعلن `X-Backend-Server` كاذبًا ليوجّه الاكتشاف نحو عنوان IP يختاره. ثمة حمايتان بنيويتان مستقلتان إحداهما عن الأخرى:
- لا تصبح أي معلومة مستمدة من هدف ما `VERIFIED` لمجرد أنها أُعلنت — تبقى لافتة `Server` أو ترويسة `X-Backend-Server` بحالة `DECLARED` مهما بدت معقولة.
- تحدّ قيود المحيط ([§4](#4-اكتشاف-الأهداف-وحدود-الأمان)) من المدى الذي يمكن أن يقود إليه هدف مُعلن (الـ `/24` الخاص نفسه، ما لم يُضبط خلاف ذلك صراحةً)، ويحدّد تأكيد المستخدم ما إذا كان سيُفحص أصلًا — فالهدف الكاذب خارج المحيط لا يُقترح حتى؛ والهدف داخل المحيط يبقى خاضعًا لتأكيد صريح قبل أي فحص.

## 11. التوافق مع الطرفيات

تكتشف واجهة TUI ‏(Textual) قدرات الطرفية تلقائيًا (المحاكي، والحجم) وتكيّف ورقة أنماطها البنيوية وفقًا لذلك (`complete`/`standard`/`reduced`/`mono`)، دون أي خيار يدوي. يبقى وضع CLI نصًا بسيطًا دائمًا، مستقلًا عن الطرفية. وهي سياسة تتشاركها مجموعة `omega-` كلها (`omega-lib`، `terminal/policies.py`).

### الملف الشخصي حسب المحاكي المكتشَف

| المحاكي | الملف الشخصي الأولي |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm، urxvt، SSH حديث | `reduced` |
| TTY في Linux، SSH قديم | `mono` |
| محاكٍ غير معروف | `reduced` (البديل الافتراضي) |

### الملف الشخصي حسب حجم الطرفية

| الحجم الأدنى (أعمدة × أسطر) | سقف الملف الشخصي |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| أقل من ذلك | `mono` |

الملف الشخصي النهائي هو **الأكثر تقييدًا بين الاثنين** (المحاكي والحجم) — فطرفية Ghostty بملء الشاشة إذا صُغّرت إلى 70 عمودًا تنزل إلى `mono`، حتى لو كان محاكيها يسمح بـ `complete`. ويمكن تحديثه مباشرة بالمفتاح `r`.

## 12. التصدير

تُكتب التقارير النصية وتقارير HTML باللغة المختارة في الإعدادات («لغة التصدير»، وهي افتراضيًا لغة الواجهة)؛ ويبقى JSON بيانات لا تُترجم. تُنشأ التقارير افتراضيًا في `var/exports/` (مسار تشغيل مرتبط بمجلد المشروع، و`$OMEGA_DEEP_VAR_DIR` لتغييره)، أو في المسار المحدد (`--output` في CLI، ومربع حوار في TUI). اسم ملف واضح ومؤرّخ: `analyse-{ملف-التعريف}-{التاريخ}.ext`، و`analyse-custom-{التاريخ}.ext` لملف تعريف شخصي.

### JSON، المرجع

البنية الكاملة للتحليل (`Scan` + `Host[]` + `ArchitectureGraph`)، قابلة للتسلسل إلى JSON بصرامة، بما في ذلك مستويات الثقة.

### النص، تقرير مقروء موجز

مقروء خارج الطرفية، دون رموز ANSI — والمخطط على شكل قائمة أضلاع.

### HTML، تقرير ويب مستقل

خمس سمات للاختيار (`--theme` في CLI، ومنتقٍ في TUI؛ ويتبع افتراضيًا سمة الواجهة النشطة عند وجود مقابل لها). تخطيط خاص: حاوية، وشبكة معلومات، ومربعات إحصاءات حسب حالة المنفذ، وشارات ملوّنة، و**رسم SVG لمخطط البنية** (انظر [§8](#8-مخطط-البنية)) — من العائلة البصرية نفسها لـ `omega-scan`/`omega-check`.

## 13. السجل والمقارنة

يُحفظ كل تحليل (SQLite، `var/db/omega-deep.db`): يضم `scan_id` واحد الهدفَ الجذري **و**جميع المضيفين المكتشفين/المقبولين، إضافة إلى المخطط المُعاد بناؤه. سجل قابل للتصفح حسب الهدف الجذري (مع عمود مخصص لعدد الأهداف المكتشفة)، وتفاصيل تحليل سابق (المضيفون + المخطط)، ومقارنة بين تحليلين (حالة منافذ **الهدف الجذري** فقط — مقارنة مخططات الاكتشاف توسعة ممكنة، غير ضرورية حتى الآن)، وإعادة تشغيل تحليل على الهدف الجذري نفسه دون إعادة إدخاله.
