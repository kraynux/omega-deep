**Omega-deep** ทำได้ทุกอย่างที่ `omega-check` ทำบนเป้าหมายเดียว (สแกนพอร์ต ระบุบริการ บทบาท WAF TLS) และเพิ่ม **การค้นพบเป้าหมายอื่นเพิ่มเติม** จากเบาะแสที่เป้าหมายที่สแกนแล้วทิ้งไว้ (ส่วนหัว การเปลี่ยนเส้นทาง ใบรับรอง ลิงก์ HTML) ภายใต้ **ขีดจำกัดความปลอดภัยที่เข้มงวด** และ **การยืนยันอย่างชัดเจนจากผู้ใช้** ก่อนสแกนเป้าหมายใดที่ค้นพบ จากนั้นจึง **สร้างกราฟสถาปัตยกรรมขึ้นใหม่** (ใครคุยกับใคร ด้วยความเชื่อมั่นระดับใด) เป็นเครื่องมือหนึ่งในชุด `omega-` จัดโครงสร้างตาม Clean Architecture — รายละเอียดทางเทคนิคทั้งหมดดูที่ `docs/ARCHITECTURE.md`

## 1. วิสัยทัศน์และขอบเขต

Omega-deep ตอบคำถามที่ omega-check ไม่ได้ถาม: *เบื้องหลัง IP นี้ยังมีอะไรอีก?* รีเวิร์สพร็อกซีที่ประกาศแบ็กเอนด์ของตน ใบรับรองที่ครอบคลุมหลายโฮสต์ หน้าเว็บที่ชี้ไปยังบริการข้างเคียง — ล้วนเป็นเบาะแสที่ omega-deep ติดตามอย่างระมัดระวัง และไม่เคยทำเองโดยพลการ

### สิ่งที่ Omega-deep ทำ

- สแกนเป้าหมายราก (root) แบบเดียวกับ omega-check ทุกประการ (โปรไฟล์ระบบ หรือโปรไฟล์ส่วนตัวที่บันทึกไว้)
- ค้นพบเป้าหมายที่เป็นไปได้จากเบาะแสที่แต่ละโฮสต์ที่สแกนแล้วทิ้งไว้: ส่วนหัว HTTP (`X-Forwarded-Host`, `X-Real-IP`, `X-Backend-Server`, `Via`) การเปลี่ยนเส้นทาง (`Location`) ใบรับรอง TLS (SAN) ลิงก์ HTML — ดู [§4](#4-การค้นพบเป้าหมายและขีดจำกัดความปลอดภัย)
- **ไม่เคย** สแกนเป้าหมายที่ค้นพบโดยไม่ได้รับการยืนยันอย่างชัดเจน ทีละเป้าหมาย — การเงียบไม่เคยถือเป็นการยอมรับ
- จำกัดการค้นพบด้วยขีดจำกัดความปลอดภัยที่เข้มงวด: ความลึกสูงสุด จำนวนเป้าหมายเพิ่มเติมสูงสุด ซับเน็ตที่อนุญาต (ค่าเริ่มต้นคือช่วงไพรเวตเดียวกับเป้าหมายราก)
- สร้าง **กราฟสถาปัตยกรรม** ขึ้นใหม่จากที่มาของแต่ละเป้าหมายที่ยอมรับ (`proxy_to`, `redirect_to`, `linked_to`) พร้อมระดับความเชื่อมั่นต่อความสัมพันธ์ — ดู [§8](#8-กราฟสถาปัตยกรรม)
- แสดงผลใน TUI (Textual) หรือ CLI ที่เขียนสคริปต์ได้ พร้อมการส่งออกสามแบบเหมือน omega-check (JSON ข้อความ HTML 5 ธีม) — ในนั้นกราฟเป็น **แผนภาพที่วาดขึ้นจริง** ใน HTML ไม่ใช่ตาราง
- ระบุระดับความเชื่อมั่นที่ชัดเจนให้กับทุกข้อมูลที่เก็บได้ (ทั้งบริการและการค้นพบ) — ดู [§9](#9-นโยบายความเชื่อมั่น)
- เก็บประวัติการวิเคราะห์ถาวร เรียกซ้ำและเปรียบเทียบข้ามเวลาได้

### สิ่งที่ Omega-deep ไม่ทำ

- สแกนช่องโหว่เชิงรุก: ไม่มี SQLi, XSS หรือ RCE
- สแกน CVE
- ระบุระบบปฏิบัติการ
- เทคนิคสแกนระดับล่างแบบ nmap (SYN scan, แพ็กเก็ตดิบ) — ใช้เฉพาะการเชื่อมต่อ TCP ระดับแอปพลิเคชัน
- เครื่องมือ brute force หรือฟัซซิง
- สแกนเป้าหมายที่ค้นพบโดยไม่ได้รับการยืนยันอย่างชัดเจนจากผู้ใช้ — ไม่เคย ไม่ว่าในโหมดใด
- ค้นพบออกไปนอกซับเน็ตไพรเวตของเป้าหมายเริ่มต้น เว้นแต่กำหนดค่าไว้อย่างชัดเจน (`--subnet`)
- แดชบอร์ดเว็บ

## 2. การติดตั้ง

### ข้อกำหนดเบื้องต้น

- Python 3.10+
- การเชื่อมต่ออินเทอร์เน็ต สำหรับติดตั้งส่วนที่ต้องพึ่งพา

### การติดตั้ง

```bash
[ -d omega-deep ] && echo "ℹ️ แตกไฟล์ไว้ที่นี่แล้ว ข้ามขั้นตอนนี้" || tar -xzf omega-deep.tar.gz
cd omega-deep/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. สร้างสภาพแวดล้อมเสมือน `.venv` หากยังไม่มี
2. ติดตั้งส่วนที่ต้องพึ่งพา (`vendor/omega-lib/` แล้วตามด้วย `pip install -e .`; `pyproject.toml` ยังคงเป็นแหล่งข้อมูลหลักเพียงแหล่งเดียว)
3. ทำให้ `omega-deep.sh` และ `install.sh` เรียกใช้งานได้
4. เพิ่มชื่อแทน `deep` ลงใน `~/.bashrc` และ `~/.zshrc` (ไม่เพิ่มซ้ำหากมีอยู่แล้ว)

### ส่วนที่ต้องพึ่งพา

ประกาศไว้ใน `pyproject.toml` (ไม่มี `requirements.txt` แล้ว):
- `omega-lib`: ไลบรารีที่ใช้ร่วมกันของชุดเครื่องมือ (`ConfidenceLevel` ธีม การตรวจจับเทอร์มินัล) — รวมมาใน `vendor/omega-lib/`
- `textual`: อินเทอร์เฟซ TUI ธีม และการปรับให้เข้ากับเทอร์มินัลโดยอัตโนมัติ
- `httpx`: ตัวตรวจ HTTP/HTTPS (บริการและการค้นพบ)
- `cryptography`: อ่านใบรับรอง TLS ที่เจรจาได้
- `jinja2`: เทมเพลตสำหรับการส่งออก HTML
- ส่วนที่ต้องพึ่งพาสำหรับการพัฒนา (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `trustme`, `ruff`, `mypy`, `import-linter`

## 3. การใช้งาน

### โหมดโต้ตอบ (TUI)

แนะนำสำหรับการใช้งานประจำวัน — เรียกโดยไม่ใส่อาร์กิวเมนต์:

```bash
./omega-deep.sh
```
หากสร้างชื่อแทนไว้แล้ว เพียงพิมพ์ `deep` ในเทอร์มินัล:
```bash
deep
```

ลำดับการใช้งาน: หน้าจอเริ่มต้น (ปิดด้วยการกดปุ่มหรือคลิก) → เมนูหลัก (วิเคราะห์ / โปรไฟล์ / ประวัติ / การตั้งค่า / ช่วยเหลือ) → กรอกเป้าหมายราก เลือกโปรไฟล์และขีดจำกัดความปลอดภัยของการค้นพบ (ความลึกสูงสุด จำนวนเป้าหมายสูงสุด ซับเน็ตที่อนุญาต) → การวิเคราะห์ (แถบความคืบหน้าแบบไม่ระบุและบันทึกการทำงานเครือข่ายสด) → ทุกครั้งที่พบเป้าหมายชุดใหม่ จะมีหน้าจอยืนยัน (หนึ่งบรรทัดต่อหนึ่งเป้าหมาย แสดงแหล่งที่มา/ความเชื่อมั่น/หลักฐาน พร้อมสวิตช์ยอมรับ/ปฏิเสธ — ค่าเริ่มต้นไม่มีการติ๊กใด ๆ) → รายละเอียดการวิเคราะห์ (โฮสต์ พอร์ต/บริการ/บทบาท กราฟ การส่งออก) → ประวัติ/การเปรียบเทียบ/การเรียกซ้ำ และการตั้งค่าจากเมนูหลัก การปรับให้เข้ากับเทอร์มินัล (สี ขนาด การลดทอนโครงสร้าง) เป็นไปโดยอัตโนมัติ

### ภาษาของอินเทอร์เฟซ

อินเทอร์เฟซมีให้ใช้ 17 ภาษา: ฝรั่งเศส อังกฤษ สเปน โปรตุเกส (บราซิล) อิตาลี เยอรมัน ดัตช์ โปแลนด์ รัสเซีย จีนตัวย่อ เวียดนาม ไทย อินโดนีเซีย ญี่ปุ่น เกาหลี ฮินดี และอาหรับ เลือกได้ในการตั้งค่า (“Langue / Language”) และมีผลหลังจากรีสตาร์ตอินเทอร์เฟซ ตัวแปร `OMEGA_DEEP_LANG` (เช่น `OMEGA_DEEP_LANG=th ./omega-deep.sh`) ใช้บังคับภาษาสำหรับหนึ่งเซสชัน เมื่อเปิดจาก omega-suite แล้ว omega-deep จะใช้ภาษาของชุดเครื่องมือ บนคอนโซลข้อความของ Linux (TTY) ภาษาที่ไม่ได้ใช้อักษรละตินจะแสดงเป็นภาษาอังกฤษตลอดเซสชันนั้น บรรทัดคำสั่งยังคงเป็นภาษาฝรั่งเศส

### โหมดสคริปต์ (CLI)

คำสั่งย่อยใดก็ตามจะเปิดโหมด CLI:

```bash
# วิเคราะห์เป้าหมาย (สแกนเป้าหมายราก + ค้นพบหลายเป้าหมาย)
./omega-deep.sh analyze 192.168.1.10 --profile web --max-depth 3 --max-targets 10 --subnet 192.168.1.0/24

# ประวัติ (กรองตามเป้าหมายรากได้)
./omega-deep.sh history --target 192.168.1.10 --limit 20

# รายละเอียดการวิเคราะห์ (ข้อความ, JSON หรือ HTML) — เลือกธีมการส่งออกได้ 5 แบบ
./omega-deep.sh show <scan_id> --format html --theme omega-base --output report.html

# เปรียบเทียบการวิเคราะห์สองครั้ง (สถานะพอร์ตของเป้าหมายราก)
./omega-deep.sh compare <scan_id_a> <scan_id_b>

# โปรไฟล์พอร์ตส่วนตัว
./omega-deep.sh profile list
./omega-deep.sh profile create lab --ports 22,80,443 --description "โปรไฟล์ของฉัน"
./omega-deep.sh profile edit lab --ports 22,80,443,8080
./omega-deep.sh profile pin lab
./omega-deep.sh profile unpin lab
./omega-deep.sh profile delete lab
```

ใน CLI เป้าหมายที่ค้นพบจะได้รับการยืนยันผ่านคำถามแบบโต้ตอบทีละเป้าหมาย (`Scanner <cible> ? [o/N]` เป็นภาษาฝรั่งเศสเหมือนส่วนอื่นของบรรทัดคำสั่ง) โดยแสดงรายละเอียดหลักฐานก่อนทุกคำถาม `--auto-validate` จะยอมรับทั้งหมดโดยไม่ตรวจทาน (**ไม่แนะนำ** มีคำเตือนแสดง) ในสภาพแวดล้อมที่ไม่โต้ตอบ (ไม่มี TTY และไม่มี `--auto-validate`) เป้าหมายที่ค้นพบทั้งหมดจะถูกปฏิเสธโดยค่าเริ่มต้น แทนที่จะถูกสแกนโดยไม่ได้รับการยืนยัน

### รูปแบบเป้าหมายที่รับได้

```text
192.168.1.10                IPv4
example.org                 ชื่อโฮสต์
http://example.org          URL แบบ HTTP  (ตัดโปรโตคอลออกก่อนแปลงชื่อ)
https://example.org:8443    URL แบบ HTTPS พร้อมพอร์ต  (ตัดโปรโตคอลและพอร์ตออก)
```

โปรโตคอลและพอร์ต (ถ้ามี) จะถูกตัดออกก่อนแปลงชื่อ DNS (`domain/targets/validation.py::normalize_target_input`) — วาง URL ทั้งหมดก็ใช้ได้ ระบบจะเก็บไว้เฉพาะโฮสต์ ส่วนเป้าหมาย *ที่ค้นพบ* จะถูกปรับรูปแบบด้วยวิธีเดียวกัน แต่ไม่เคยถูกสแกนโดยไม่ได้รับการยืนยัน (ดู [§4](#4-การค้นพบเป้าหมายและขีดจำกัดความปลอดภัย))

## 4. การค้นพบเป้าหมายและขีดจำกัดความปลอดภัย

### แหล่งเบาะแส

| แหล่ง | ที่มา | ความเชื่อมั่น |
|---|---|---|
| `header` | `X-Forwarded-Host`, `X-Real-IP`, `X-Backend-Server`, `Via` | `DECLARED` |
| `redirection` | ส่วนหัว `Location` ของการตอบกลับ HTTP | `DECLARED` |
| `certificate` | SAN (Subject Alternative Names) ของใบรับรอง TLS ที่เจรจาได้ | `DECLARED` |
| `html_link` | ลิงก์ (`<a href>`) ที่หน้าเว็บส่งมา | `INFERRED` |

ค่า `DECLARED` ยังคงเป็นการประกาศของเป้าหมายเอง (ปลอมแปลงได้) — ดู [§10](#10-การป้องกันค่าที่ถูกปลอมแปลง) ส่วน `html_link` ถูกกำหนดให้เป็นแหล่งที่อ่อนที่สุดโดยเจตนา: ลิงก์ธรรมดาไม่ได้ประกาศความสัมพันธ์ด้านโครงสร้างพื้นฐานใด ๆ

### ขีดจำกัดความปลอดภัย (ทำงานเสมอ ปิดไม่ได้)

- **ขอบเขต**: เป้าหมายที่เป็นไปได้ต้องเป็น IP ไพรเวตใน `/24` เดียวกับเป้าหมายราก เว้นแต่ระบุ `--subnet` อย่างชัดเจน (ในกรณีนั้นจะพิจารณาเพียงว่าอยู่ในซับเน็ตที่ระบุหรือไม่ แม้จะครอบคลุม IP สาธารณะก็ตาม — การกำหนดค่าอย่างชัดเจนคือสิ่งที่อนุญาตข้อยกเว้นนี้) ชื่อโฮสต์ที่ยังไม่ได้แปลงชื่อจะไม่ผ่านตัวกรองนี้เลย (การแปลงชื่อเพื่อตรวจสอบก็ถือเป็นการกระทำทางเครือข่ายที่เกินขอบเขตของการตรวจนี้แล้ว)
- **ความลึก**: `--max-depth` (ค่าเริ่มต้น 3) — สูงสุด A → B → C → D
- **จำนวนเป้าหมาย**: `--max-targets` (ค่าเริ่มต้น 10) — รวมทุกระดับความลึก

### การยืนยัน (ไม่สแกนเลยหากไม่มีการยืนยัน)

แต่ละเป้าหมายที่เสนอจะผ่าน `PROPOSED → PRESENTED → ACCEPTED` หรือ `REJECTED` กฎนี้ **ปลอดภัยเมื่อเกิดความผิดพลาด**: เป้าหมายใดที่ไม่เคยได้รับการยอมรับอย่างชัดเจน (เงียบ ปิดหน้าจอ ถูกขัดจังหวะ หมดเวลา ไม่มี TTY) จะถือว่าถูกปฏิเสธ — ไม่เคยกลับกัน ใน TUI มีหน้าจอเฉพาะที่แสดงเป้าหมายของชุดพร้อมหลักฐานและความเชื่อมั่น สวิตช์ยอมรับ/ปฏิเสธในแต่ละบรรทัด “ยอมรับทั้งหมด”/“ปฏิเสธทั้งหมด” และปฏิเสธทั้งหมดเป็นค่าเริ่มต้นเมื่อกด Esc ใน CLI จะถามหนึ่งคำถามต่อเป้าหมาย; `--auto-validate` (ไม่แนะนำ) เป็นวิธีเดียวที่จะข้ามการโต้ตอบ

## 6. สถาปัตยกรรม

Omega-deep จัดโครงสร้างตาม **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins / shared) สอดคล้องกับแม่แบบของชุด `omega-` (ดู `omega-scan`/`omega-check`) และตรวจสอบด้วย `import-linter` ทุกครั้งที่แก้ไข รายละเอียดทั้งหมดอยู่ใน **`docs/ARCHITECTURE.md`**

ภาพรวมแบบสั้นมาก:

```text
src/omega_deep/
├── domain/          ตรรกะทางธุรกิจล้วน: การสแกน เป้าหมาย บริการ โปรไฟล์ รายงาน
│                    discovery (เป้าหมายที่เสนอ เครื่องสถานะของการยืนยัน)
│                    architecture (กราฟ กฎความสัมพันธ์)
├── application/     กรณีการใช้งาน (commands/queries) — รวมถึง discover_targets,
│                    validate_targets, reconstruct_architecture (ใหม่เมื่อเทียบกับ omega-check)
├── ports/           สัญญาที่แอปพลิเคชันคาดหวัง (ตัวตรวจ รวมถึง discovery_prober
│                    ที่เก็บข้อมูล ตัวส่งออก...)
├── infrastructure/  การทำงานจริง (socket/httpx/cryptography, SQLite,
│                    การวาดกราฟเป็น SVG — Textual ไม่ได้อยู่ที่นี่)
├── interfaces/      tui/ (Textual) และ cli/ (เขียนสคริปต์ได้) ความสามารถเท่ากันอย่างเคร่งครัด
├── app/             การประกอบ (DependencyContainer, bootstrap, วงจรชีวิต)
├── core/, shared/   คำศัพท์ร่วม เครื่องมือที่ไม่เกี่ยวกับธุรกิจ
└── plugins/         วางโครงสร้างไว้แล้ว ยังว่าง (ยังไม่มีแนวทางขยายที่ยืนยันแล้ว)
```

กฎการออกแบบ:
- `domain/services/policies.py`: จัดประเภทเบาะแสที่เก็บได้แล้ว ไม่เข้าถึงเครือข่ายเลย
- `domain/discovery/policies.py`: ขีดจำกัดความปลอดภัยด้านขอบเขต/ความลึก/จำนวน — ตรรกะล้วน ทดสอบได้โดยไม่ต้องใช้เครือข่าย
- `domain/architecture/service.py`: สร้างกราฟขึ้นใหม่จากที่มาที่แต่ละ `Host` มีอยู่แล้ว ไม่ส่งคำขอใหม่
- `infrastructure/network/` และ `infrastructure/discovery/`: ทำงานกับเครือข่าย (ซ็อกเก็ต, `httpx`, `cryptography`) ไม่ตัดสินใด ๆ
- `interfaces/`: แสดงผล ไม่มีตรรกะทางธุรกิจ — หน้าจอยืนยันเป้าหมายที่ค้นพบเรียกใช้ `validate_targets` และไม่ได้ทำกฎความปลอดภัยเมื่อเกิดความผิดพลาดเอง
- `infrastructure/exporters/`: อ่านผลการวิเคราะห์ (การสแกน โฮสต์ กราฟ) ไม่คำนวณสิ่งใดใหม่

## 7. การระบุบริการและบทบาท

### โปรโตคอลที่ตรวจพบ

| โปรโตคอล | วิธีตรวจ | รายละเอียดที่เก็บ |
|---|---|---|
| HTTP / HTTPS | `httpx` | แบนเนอร์ `Server` ส่วนหัวการยืนยันตัวตน |
| TLS | `cryptography` (ใบรับรองที่เจรจาได้ รวมถึง `CERT_NONE`) | เวอร์ชัน ชุดการเข้ารหัส ผู้ถือ/ผู้ออกใบรับรอง |
| SSH | แบนเนอร์ดิบ | ซอฟต์แวร์และเวอร์ชัน (เช่น `OpenSSH 10.4`) |
| VNC (RFB) | รหัสความปลอดภัยที่เซิร์ฟเวอร์ประกาศ | ประเภทการยืนยันตัวตนที่รองรับ |
| ทั่วไป | แบนเนอร์ดิบบนพอร์ตที่เปิดแต่ไม่รู้จัก | ดึงข้อมูลอย่างระมัดระวัง ไม่ใช้ฮิวริสติกที่รุนแรง |

### บทบาทที่อนุมาน

อนุมานจากโปรโตคอลที่ **เจรจาได้จริง** ไม่ใช่การเดาจากหมายเลขพอร์ต:

| บทบาท | เงื่อนไข | ความเชื่อมั่น |
|---|---|---|
| `เว็บเซิร์ฟเวอร์` | ยืนยันโปรโตคอล HTTP/HTTPS แล้ว | `INFERRED` |
| `การเข้าถึงเชลล์` | ยืนยันโปรโตคอล SSH แล้ว | `CORROBORATED` |
| `การเข้าถึงแบบกราฟิก` | ยืนยันโปรโตคอล VNC แล้ว | `CORROBORATED` |
| `ฐานข้อมูล` | พอร์ตอยู่ในช่วงของโปรไฟล์ระบบ `db` | `INFERRED` |

### ลายเซ็น WAF ที่รู้จัก

ตรวจพบผ่านส่วนหัวเชิงประกาศ (`server`, `x-sdk`) — การมีอยู่ **ประกาศโดยเป้าหมายเอง** ไม่เคยตรวจสอบโดยอิสระ: Cloudflare, Sucuri, Akamai, Imperva Incapsula, AWS ELB (ระบุไว้เพื่อเป็นข้อมูล ไม่ได้เป็น WAF ระดับแอปพลิเคชันโดยแท้)

## 8. กราฟสถาปัตยกรรม

สร้างขึ้นใหม่จากที่มาที่แต่ละโฮสต์ที่ยอมรับมีอยู่แล้วเท่านั้น (`discovered_from`/`discovery_source`/`discovery_confidence`) — ไม่มีคำขอเครือข่ายใหม่ ไม่วิเคราะห์เบาะแสดิบซ้ำ

### ความสัมพันธ์ที่สร้างขึ้น

| ความสัมพันธ์ | แหล่งการค้นพบ | ความหมาย |
|---|---|---|
| `proxy_to` | `header` | เป้าหมายราก (หรือโฮสต์ที่ยอมรับแล้ว) น่าจะเป็นพร็อกซีไปยังเป้าหมายที่ค้นพบ |
| `redirect_to` | `redirection` | พบการเปลี่ยนเส้นทาง HTTP ไปยังเป้าหมายที่ค้นพบ |
| `linked_to` | `certificate` หรือ `html_link` | ความสัมพันธ์ที่เป็นกลางที่สุด — ใช้โครงสร้างพื้นฐาน/แอปพลิเคชันร่วมกัน โดยไม่ระบุทิศทางการไหลของข้อมูล |

`backend_of` (เส้นย้อนกลับของ `proxy_to`) ไม่ถูกสร้างโดยเจตนา — เพราะจะเป็นข้อมูลซ้ำ ไม่ใช่ข้อสรุปใหม่

### การแสดงผล

- **TUI** (รายละเอียดการวิเคราะห์) และ **การส่งออก JSON/ข้อความ**: รายการเส้นเชื่อม (ต้นทาง ความสัมพันธ์ ปลายทาง ความเชื่อมั่น) — เทอร์มินัลไม่ใช่ที่สำหรับการแสดงผลกราฟิกที่ซับซ้อน
- **การส่งออก HTML**: **แผนภาพ SVG จริง** (โหนด = วงกลม เส้น = ลูกศรที่มีป้าย) จัดวางเป็นชั้นโดยคำนวณจากเป้าหมายราก ขนาดแปรตามจำนวนเครื่องที่ค้นพบ — ไม่พึ่งพาไลบรารีจัดวางกราฟหนัก ๆ; โดยการออกแบบกราฟจึงมีขนาดเล็กเสมอ (ถูกจำกัดด้วยขีดจำกัดความปลอดภัยใน [§4](#4-การค้นพบเป้าหมายและขีดจำกัดความปลอดภัย))

## 9. นโยบายความเชื่อมั่น

ทุกช่องข้อมูลที่เก็บได้จะมีระดับใดระดับหนึ่งต่อไปนี้:

| ระดับ | ความหมาย |
|---|---|
| `VERIFIED` | ข้อเท็จจริงของโปรโตคอลที่สังเกตได้โดยตรง เป้าหมายปลอมแปลงไม่ได้ (เช่น พอร์ตปิดที่ยืนยันด้วย TCP RST เวอร์ชัน TLS ที่เจรจาได้จริง) |
| `DECLARED` | ค่าที่เป้าหมายประกาศเองในช่องที่ควบคุมได้ทั้งหมด (เช่น แบนเนอร์ `Server` ส่วนหัว `X-Backend-Server`) — ดูน่าเชื่อแต่ปลอมแปลงได้ตามใจ |
| `CORROBORATED` | ค่า `DECLARED` ที่ได้รับการยืนยันจากเบาะแสอิสระ (เช่น บทบาท SSH เพราะโปรโตคอลเจรจาได้จริง) |
| `INFERRED` | อนุมานจากรูปแบบ/ฮิวริสติก โดยเป้าหมายไม่ได้ประกาศอย่างชัดเจน (เช่น ลิงก์ HTML) |
| `UNKNOWN` | ไม่มีเบาะแสที่ใช้ได้ หรือเป้าหมายจงใจซ่อน |

## 10. การป้องกันค่าที่ถูกปลอมแปลง

Omega-deep ไม่เชื่อข้อมูลใดที่เป้าหมายประกาศเองโดยไม่ระบุอย่างชัดเจน — และการค้นพบเป้าหมายคือส่วนที่อ่อนไหวที่สุดของโปรเจกต์: เป้าหมายที่ประสงค์ร้าย *อาจ* ประกาศ `X-Backend-Server` ปลอมเพื่อชักนำการค้นพบไปยัง IP ที่ตนเลือก มีการป้องกันเชิงโครงสร้างสองชั้นที่เป็นอิสระต่อกัน:
- ไม่มีข้อมูลใดที่ได้มาจากเป้าหมายจะกลายเป็น `VERIFIED` เพียงเพราะถูกประกาศ — แบนเนอร์ `Server` หรือส่วนหัว `X-Backend-Server` ยังคงเป็น `DECLARED` ไม่ว่าจะดูน่าเชื่อเพียงใด
- ขีดจำกัดด้านขอบเขต ([§4](#4-การค้นพบเป้าหมายและขีดจำกัดความปลอดภัย)) จำกัดว่าเป้าหมายที่ถูกประกาศจะนำไปได้ถึงไหน (`/24` ไพรเวตเดียวกัน เว้นแต่กำหนดค่าไว้ชัดเจน) และการยืนยันของผู้ใช้กำหนดว่าจะสแกนหรือไม่ — เป้าหมายปลอมที่อยู่นอกขอบเขตจะไม่ถูกเสนอเลย ส่วนเป้าหมายในขอบเขตยังต้องได้รับการยืนยันอย่างชัดเจนก่อนการสแกนใด ๆ

## 11. ความเข้ากันได้กับเทอร์มินัล

TUI (Textual) ตรวจจับความสามารถของเทอร์มินัล (อีมูเลเตอร์ ขนาด) โดยอัตโนมัติ และปรับสไตล์ชีตเชิงโครงสร้างให้เหมาะสม (`complete`/`standard`/`reduced`/`mono`) โดยไม่ต้องตั้งค่าเอง โหมด CLI เป็นข้อความธรรมดาเสมอ ไม่ขึ้นกับเทอร์มินัล เป็นนโยบายที่ใช้ร่วมกันทั้งชุด `omega-` (`omega-lib`, `terminal/policies.py`)

### โปรไฟล์ตามอีมูเลเตอร์ที่ตรวจพบ

| อีมูเลเตอร์ | โปรไฟล์เริ่มต้น |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, SSH รุ่นใหม่ | `reduced` |
| TTY ของ Linux, SSH รุ่นเก่า | `mono` |
| อีมูเลเตอร์ที่ไม่รู้จัก | `reduced` (ค่าสำรองเริ่มต้น) |

### โปรไฟล์ตามขนาดเทอร์มินัล

| ขนาดขั้นต่ำ (คอลัมน์ × บรรทัด) | เพดานโปรไฟล์ |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| ต่ำกว่านั้น | `mono` |

โปรไฟล์สุดท้ายคือ **โปรไฟล์ที่เข้มงวดกว่าในสองแบบ** (อีมูเลเตอร์และขนาด) — Ghostty แบบเต็มจอที่ถูกย่อเหลือ 70 คอลัมน์จะลดลงเป็น `mono` แม้อีมูเลเตอร์จะรองรับ `complete` ก็ตาม รีเฟรชสดได้ด้วยแป้น `r`

## 12. การส่งออก

รายงานข้อความและ HTML เขียนด้วยภาษาที่เลือกในการตั้งค่า (“ภาษาของการส่งออก” ค่าเริ่มต้นคือภาษาของอินเทอร์เฟซ) ส่วน JSON ยังคงเป็นข้อมูลและไม่ถูกแปล รายงานถูกสร้างใน `var/exports/` เป็นค่าเริ่มต้น (เส้นทางขณะทำงานยึดกับโฟลเดอร์โปรเจกต์ ใช้ `$OMEGA_DEEP_VAR_DIR` เพื่อเปลี่ยน) หรือที่เส้นทางที่ระบุ (`--output` ใน CLI กล่องโต้ตอบใน TUI) ชื่อไฟล์ชัดเจนและมีเวลากำกับ: `analyse-{โปรไฟล์}-{วันที่}.ext` และ `analyse-custom-{วันที่}.ext` สำหรับโปรไฟล์ส่วนตัว

### JSON แหล่งข้อมูลหลัก

โครงสร้างทั้งหมดของการวิเคราะห์ (`Scan` + `Host[]` + `ArchitectureGraph`) แปลงเป็น JSON ได้อย่างเคร่งครัด รวมระดับความเชื่อมั่น

### ข้อความ รายงานกะทัดรัดสำหรับอ่าน

อ่านได้นอกเทอร์มินัล ไม่มีรหัส ANSI — กราฟอยู่ในรูปรายการเส้นเชื่อม

### HTML รายงานเว็บแบบสมบูรณ์ในตัว

เลือกได้ 5 ธีม (`--theme` ใน CLI ตัวเลือกใน TUI; ค่าเริ่มต้นจะตามธีมอินเทอร์เฟซที่ใช้อยู่หากมีธีมที่ตรงกัน) เลย์เอาต์เฉพาะ: คอนเทนเนอร์ ตารางข้อมูล กล่องสถิติตามสถานะพอร์ต ป้ายสี **แผนภาพ SVG ของกราฟสถาปัตยกรรม** (ดู [§8](#8-กราฟสถาปัตยกรรม)) — อยู่ในตระกูลภาพเดียวกับ `omega-scan`/`omega-check`

## 13. ประวัติและการเปรียบเทียบ

ทุกการวิเคราะห์ถูกบันทึกไว้ (SQLite, `var/db/omega-deep.db`): หนึ่ง `scan_id` ครอบคลุมเป้าหมายราก **และ** ทุกโฮสต์ที่ค้นพบ/ยอมรับ พร้อมกราฟที่สร้างขึ้นใหม่ เปิดดูประวัติตามเป้าหมายรากได้ (มีคอลัมน์เฉพาะสำหรับจำนวนเป้าหมายที่ค้นพบ) ดูรายละเอียดการวิเคราะห์ที่ผ่านมา (โฮสต์ + กราฟ) เปรียบเทียบการวิเคราะห์สองครั้ง (เฉพาะสถานะพอร์ตของ **เป้าหมายราก** — การเปรียบเทียบกราฟการค้นพบอาจเป็นส่วนขยายในอนาคต ปัจจุบันยังไม่จำเป็น) และเรียกวิเคราะห์ซ้ำกับเป้าหมายรากเดิมโดยไม่ต้องกรอกใหม่

## 14. การทดสอบ

```bash
source .venv/bin/activate
lint-imports        # ตรวจ Dependency Rule
pytest -q           # 191 การทดสอบ
ruff check src tests
mypy -p omega_deep
```

โครงสร้าง: `tests/unit/` (โดเมนและแอปพลิเคชัน ไม่มี I/O จริง), `tests/integration/` (SQLite/ไฟล์จริง เซิร์ฟเวอร์ HTTP จำลอง `pytest-httpserver` และ TLS ผ่าน `trustme`), `tests/tui/` (การนำทางผ่าน `Pilot` เชิงโครงสร้าง — ไม่อ้างว่าตรวจสอบภาพเอง)
