**Omega-deep** делает всё то же, что `omega-check` на одной цели (сканирование портов, определение служб, роли, WAF, TLS), и добавляет **обнаружение дополнительных целей** по признакам, оставленным уже просканированной целью (заголовки, перенаправления, сертификат, HTML-ссылки), в **строгих защитных рамках** и с **явным подтверждением пользователя** перед сканированием любой обнаруженной цели, а затем **восстанавливает граф архитектуры** (кто с кем общается и с какой степенью доверия). Инструмент набора `omega-`, построенный по принципам Clean Architecture — все технические подробности см. в `docs/ARCHITECTURE.md`.

## 1. Назначение и границы

Omega-deep отвечает на вопрос, которого не задаёт omega-check: *что ещё скрывается за этим IP?* Обратный прокси, объявляющий свой бэкенд, сертификат на несколько хостов, страница, указывающая на соседнюю службу, — всё это признаки, по которым omega-deep идёт осторожно и никогда не самовольно.

### Что делает Omega-deep

- Сканирует корневую цель точно так же, как omega-check (системный профиль или сохранённый личный профиль).
- Находит цели-кандидаты по признакам, оставленным каждым уже просканированным хостом: HTTP-заголовки (`X-Forwarded-Host`, `X-Real-IP`, `X-Backend-Server`, `Via`), перенаправление (`Location`), сертификат TLS (SAN), HTML-ссылки — см. [§4](#4-обнаружение-целей-и-защитные-рамки).
- **Никогда** не сканирует обнаруженную цель без явного подтверждения, цель за целью — молчание никогда не считается согласием.
- Ограничивает обнаружение строгими защитными рамками: максимальная глубина, максимальное число дополнительных целей, разрешённая подсеть (по умолчанию тот же частный диапазон, что у корня).
- Восстанавливает **граф архитектуры** по происхождению каждой принятой цели (`proxy_to`, `redirect_to`, `linked_to`), с уровнем доверия для каждой связи — см. [§8](#8-граф-архитектуры).
- Показывает результат в TUI (Textual) или в CLI для сценариев, с теми же тремя видами экспорта, что у omega-check (JSON, текст, HTML с 5 темами), — граф там **настоящая нарисованная диаграмма** в HTML, а не таблица.
- Присваивает каждому собранному сведению (о службе или об обнаружении) явный уровень доверия — см. [§9](#9-политика-доверия).
- Хранит постоянную историю анализов, которые можно повторять и сравнивать во времени.

### Чего Omega-deep не делает

- Активное сканирование уязвимостей: никаких SQLi, XSS или RCE.
- Сканирование CVE.
- Определение операционной системы.
- Низкоуровневые техники сканирования в духе nmap (SYN-сканирование, сырые пакеты) — только TCP-соединения прикладного уровня.
- Перебор паролей или фаззинг.
- Сканирование обнаруженной цели без явного подтверждения пользователя — никогда, ни в каком режиме.
- Обнаружение за пределами частной подсети исходной цели, если это явно не настроено (`--subnet`).
- Веб-панель.

## 2. Установка

### Требования

- Python 3.10+
- Подключение к Интернету, для зависимостей

### Установка

```bash
[ -d omega-deep ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-deep.tar.gz
cd omega-deep/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если его ещё нет.
2. Устанавливает зависимости (`vendor/omega-lib/`, затем `pip install -e .`; `pyproject.toml` остаётся единственным источником истины).
3. Делает `omega-deep.sh` и `install.sh` исполняемыми.
4. Добавляет псевдоним `deep` в `~/.bashrc` и `~/.zshrc` (без дублирования, если он уже есть).

### Зависимости

Объявлены в `pyproject.toml` (`requirements.txt` больше нет):
- `omega-lib`: общая библиотека набора (`ConfidenceLevel`, темы, определение терминала) — поставляется в `vendor/omega-lib/`
- `textual`: интерфейс TUI, темы, автоматическая подстройка под терминал
- `httpx`: зонды HTTP/HTTPS (службы и обнаружение)
- `cryptography`: чтение согласованного сертификата TLS
- `jinja2`: шаблоны для экспорта в HTML
- Зависимости для разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `trustme`, `ruff`, `mypy`, `import-linter`

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для повседневной работы — запускается без аргументов:

```bash
./omega-deep.sh
```
если вы создали псевдоним, просто наберите `deep` в терминале:
```bash
deep
```

Порядок работы: заставка (закрывается нажатием клавиши или щелчком) → главное меню (Анализировать / Профили / История / Настройки / Справка) → ввод корневой цели, выбор профиля и защитных рамок обнаружения (макс. глубина, макс. число целей, разрешённая подсеть) → анализ (неопределённый индикатор и журнал сетевых операций в реальном времени) → для каждой партии обнаруженных целей — экран подтверждения (одна строка на цель, с источником/доверием/доказательством, переключатель «принять/отклонить» — по умолчанию ничего не отмечено) → подробности анализа (хосты, порты/службы/роли, граф, экспорт) → история/сравнение/повтор и настройки из главного меню. Подстройка под терминал (цвета, размер, упрощение структуры) происходит автоматически.

#### Сочетания клавиш

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Переход между элементами экрана |
| `Tab` / `Shift+Tab` | Переход между полями формы |
| `Esc` | Возврат на предыдущий экран (подтверждение выхода на главном экране) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить определение терминала |
| `a` | Показать справку |
| `q` | Выйти (с подтверждением) |

### Языки интерфейса

Интерфейс доступен на 17 языках: французском, английском, испанском, португальском (Бразилия), итальянском, немецком, нидерландском, польском, русском, упрощённом китайском, вьетнамском, тайском, индонезийском, японском, корейском, хинди и арабском. Язык выбирается в Настройках («Langue / Language») и применяется после перезапуска интерфейса; переменная `OMEGA_DEEP_LANG` (например, `OMEGA_DEEP_LANG=ru ./omega-deep.sh`) задаёт язык на один сеанс. При запуске из omega-suite omega-deep использует язык набора. В текстовой консоли Linux (TTY) языки с нелатинской письменностью на время сеанса показываются по-английски. Командная строка остаётся на французском.

### Контакты и поддержка

Справка (клавиша `a`) предлагает экран **Контакты и поддержка**: *Угостить кофе* (страница PayPal разработчика), *Связаться с поддержкой* (адрес электронной почты и контактная форма сайта, показанные открыто), *Зарегистрироваться как пользователь (анонимно)* и *Проверить обновления*. Регистрация добровольная, по умолчанию отключена и отправляется только один раз: она служит лишь для подсчёта пользователей и, по желанию, их континента или страны (закрытые списки, никогда не свободный текст). Отправляются случайно сгенерированный ключ, название программы (`omega-deep`) и её версия; никогда имя, имя машины, настройка, цель или результат. IP-адрес не сохраняется в регистрациях, но, как при любом посещении, проходит через проверки безопасности и журнал принимающего сервера. Отозвать регистрацию можно в любой момент на том же экране (*Больше не регистрировать меня*). Проверка обновлений лишь читает список версий, опубликованных на сайте, и никогда без щелчка.

### Режим для сценариев (CLI)

Любая подкоманда включает режим CLI:

```bash
# Анализ цели (сканирование корня + обнаружение нескольких целей)
./omega-deep.sh analyze 192.168.1.10 --profile web --max-depth 3 --max-targets 10 --subnet 192.168.1.0/24

# История (с фильтром по корневой цели)
./omega-deep.sh history --target 192.168.1.10 --limit 20

# Подробности анализа (текст, JSON или HTML) — на выбор 5 тем экспорта
./omega-deep.sh show <scan_id> --format html --theme omega-base --output otchet.html

# Сравнить два анализа (состояние портов корневой цели)
./omega-deep.sh compare <scan_id_a> <scan_id_b>

# Личные профили портов
./omega-deep.sh profile list
./omega-deep.sh profile create lab --ports 22,80,443 --description "Мой профиль"
./omega-deep.sh profile edit lab --ports 22,80,443,8080
./omega-deep.sh profile pin lab
./omega-deep.sh profile unpin lab
./omega-deep.sh profile delete lab
```

В CLI обнаруженные цели подтверждаются интерактивным вопросом для каждой цели (`Scanner <cible> ? [o/N]`, по-французски, как и вся командная строка), причём перед каждым вопросом показывается доказательство. `--auto-validate` принимает всё без проверки (**не рекомендуется**, выводится предупреждение); в неинтерактивной среде (нет TTY, нет `--auto-validate`) любая обнаруженная цель по умолчанию отклоняется, а не сканируется без подтверждения.

### Допустимые форматы цели

```text
192.168.1.10                IPv4
example.org                 Имя хоста
http://example.org          URL HTTP  (схема удаляется до разрешения имени)
https://example.org:8443    URL HTTPS с портом  (схема и порт удаляются)
```

Схема и порт, если они есть, удаляются до разрешения DNS (`domain/targets/validation.py::normalize_target_input`) — можно вставить URL целиком, сохраняется только хост. *Обнаруженные* цели нормализуются так же, но никогда не сканируются без подтверждения (см. [§4](#4-обнаружение-целей-и-защитные-рамки)).

## 4. Обнаружение целей и защитные рамки

### Источники признаков

| Источник | Происхождение | Доверие |
|---|---|---|
| `header` | `X-Forwarded-Host`, `X-Real-IP`, `X-Backend-Server`, `Via` | `DECLARED` |
| `redirection` | Заголовок `Location` HTTP-ответа | `DECLARED` |
| `certificate` | SAN (Subject Alternative Names) согласованного сертификата TLS | `DECLARED` |
| `html_link` | Ссылки (`<a href>`), отдаваемые страницей | `INFERRED` |

Значение `DECLARED` остаётся самоописанием цели (его можно подделать) — см. [§10](#10-защита-от-поддельных-значений). `html_link` намеренно самый слабый источник: обычная ссылка не объявляет никакой связи на уровне инфраструктуры.

### Защитные рамки (всегда включены, никогда не отключаются)

- **Периметр**: цель-кандидат должна быть частным IP в той же сети `/24`, что и корневая цель, если явно не задан `--subnet` (тогда учитывается только принадлежность к указанной подсети, даже если она включает публичные IP, — исключение разрешает именно явная настройка). Неразрешённое имя хоста этим фильтром никогда не принимается (разрешить его ради проверки уже было бы сетевым действием за пределами этой проверки).
- **Глубина**: `--max-depth` (по умолчанию 3) — не больше A → B → C → D.
- **Число целей**: `--max-targets` (по умолчанию 10) — на всех глубинах вместе.

### Подтверждение (никакого сканирования без согласия)

Каждая предложенная цель проходит `PROPOSED → PRESENTED → ACCEPTED` или `REJECTED`. Правило **безопасно при сбое**: любая цель, ни разу явно не принятая (молчание, закрытие экрана, прерывание, тайм-аут, отсутствие TTY), считается отклонённой — и никогда наоборот. В TUI отдельный экран перечисляет цели партии с доказательством и доверием, переключателем «принять/отклонить» в каждой строке, кнопками «принять все»/«отклонить все» и полным отклонением по умолчанию клавишей Esc. В CLI — один вопрос на цель; `--auto-validate` (не рекомендуется) — единственный способ обойти интерактивность.

## 6. Архитектура

Omega-deep построен по принципам **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins / shared), согласованным с шаблоном набора `omega-` (см. `omega-scan`/`omega-check`), и проверяется `import-linter` при каждом изменении. Все подробности — в **`docs/ARCHITECTURE.md`**.

Очень краткий обзор:

```text
src/omega_deep/
├── domain/          Чистая предметная логика: сканирования, цели, службы, профили, отчёты,
│                    discovery (предложенные цели, конечный автомат подтверждения),
│                    architecture (граф, правила связей)
├── application/     Сценарии использования (commands/queries) — в том числе discover_targets,
│                    validate_targets, reconstruct_architecture (новые по сравнению с omega-check)
├── ports/           Контракты, ожидаемые приложением (зонды, в том числе discovery_prober,
│                    репозитории, экспортёры...)
├── infrastructure/  Конкретные реализации (socket/httpx/cryptography, SQLite,
│                    отрисовка графа в SVG — Textual здесь НЕТ)
├── interfaces/      tui/ (Textual) и cli/ (для сценариев), со строгим равенством возможностей
├── app/             Сборка (DependencyContainer, bootstrap, жизненный цикл)
├── core/, shared/   Общий словарь, вспомогательные средства вне предметной логики
└── plugins/         Структура заложена, пуста (ни одно направление расширения не подтверждено)
```

Правила проектирования:
- `domain/services/policies.py`: классифицирует уже собранные признаки, никогда не обращается к сети.
- `domain/discovery/policies.py`: защитные рамки периметра/глубины/числа — чистая логика, проверяемая без сети.
- `domain/architecture/service.py`: восстанавливает граф по происхождению, которое уже несёт каждый `Host`, не делает новых запросов.
- `infrastructure/network/` и `infrastructure/discovery/`: работают с сетью (сокеты, `httpx`, `cryptography`), никогда не выносят оценок.
- `interfaces/`: отображает, не содержит предметной логики — экран подтверждения обнаруженных целей вызывает `validate_targets` и сам не реализует правило безопасности при сбое.
- `infrastructure/exporters/`: читают результат анализа (сканирование, хосты, граф), ничего не пересчитывают.

## 7. Определение служб и роли

### Обнаруживаемые протоколы

| Протокол | Зонд | Собираемые сведения |
|---|---|---|
| HTTP / HTTPS | `httpx` | Баннер `Server`, заголовки аутентификации |
| TLS | `cryptography` (согласованный сертификат, включая `CERT_NONE`) | Версия, шифр, субъект/издатель сертификата |
| SSH | Сырой баннер | Программа и версия (например, `OpenSSH 10.4`) |
| VNC (RFB) | Коды безопасности, объявленные сервером | Поддерживаемые типы аутентификации |
| Общий | Сырой баннер на нераспознанном открытом порту | Осторожное извлечение, без агрессивной эвристики |

### Выводимые роли

Выводятся из **действительно согласованного** протокола, никогда — из предположения по номеру порта:

| Роль | Условие | Доверие |
|---|---|---|
| `веб-сервер` | Протокол HTTP/HTTPS подтверждён | `INFERRED` |
| `доступ к оболочке` | Протокол SSH подтверждён | `CORROBORATED` |
| `графический доступ` | Протокол VNC подтверждён | `CORROBORATED` |
| `база данных` | Порт в диапазоне системного профиля `db` | `INFERRED` |

### Известные сигнатуры WAF

Обнаруживаются по декларативному заголовку (`server`, `x-sdk`) — присутствие **объявлено самой целью** и никогда не проверяется независимо: Cloudflare, Sucuri, Akamai, Imperva Incapsula, AWS ELB (указан для сведения, строго говоря не является прикладным WAF).

## 8. Граф архитектуры

Восстанавливается только по происхождению, которое уже несёт каждый принятый хост (`discovered_from`/`discovery_source`/`discovery_confidence`), — никаких новых сетевых запросов и повторного разбора сырых признаков.

### Создаваемые связи

| Связь | Источник обнаружения | Значение |
|---|---|---|
| `proxy_to` | `header` | Корневая цель (или уже принятый хост), вероятно, является прокси к обнаруженной цели |
| `redirect_to` | `redirection` | Наблюдалось HTTP-перенаправление на обнаруженную цель |
| `linked_to` | `certificate` или `html_link` | Самая нейтральная связь — общая инфраструктура/приложение, без утверждений о направлении потока |

`backend_of` (обратное ребро к `proxy_to`) намеренно не создаётся — это было бы дублированием сведений, а не новым выводом.

### Отображение

- **TUI** (подробности анализа) и **экспорт JSON/текст**: список рёбер (источник, связь, цель, доверие) — терминал не место для богатой графики.
- **Экспорт HTML**: **настоящая SVG-диаграмма** (узлы — круги, рёбра — подписанные стрелки), послойная раскладка от корневой цели, размер пропорционален числу обнаруженных машин — никаких тяжёлых зависимостей для раскладки графов; граф по самому замыслу остаётся небольшим (его ограничивают защитные рамки из [§4](#4-обнаружение-целей-и-защитные-рамки)).

## 9. Политика доверия

Каждое собранное поле имеет один из уровней:

| Уровень | Значение |
|---|---|
| `VERIFIED` | Протокольный факт, наблюдаемый напрямую, который цель не может подделать (например, закрытый порт, подтверждённый TCP RST, действительно согласованная версия TLS). |
| `DECLARED` | Значение, объявленное самой целью в поле, которое она полностью контролирует (например, баннер `Server`, заголовок `X-Backend-Server`), — правдоподобно, но подделывается как угодно. |
| `CORROBORATED` | Значение `DECLARED`, подтверждённое независимым признаком (например, роль SSH, поскольку протокол действительно был согласован). |
| `INFERRED` | Выведено из шаблона/эвристики, без явного объявления со стороны цели (например, HTML-ссылка). |
| `UNKNOWN` | Нет пригодных признаков, или цель активно их скрывает. |

## 10. Защита от поддельных значений

Omega-deep не доверяет никаким данным, объявленным самой целью, не помечая этого явно, — а обнаружение целей самая чувствительная часть проекта: вредоносная цель *могла бы* объявить ложный `X-Backend-Server`, чтобы направить обнаружение на IP по своему выбору. Две структурные защиты, не зависящие друг от друга:
- Никакое сведение, полученное от цели, никогда не становится `VERIFIED` лишь потому, что оно объявлено, — баннер `Server` или заголовок `X-Backend-Server` остаются `DECLARED`, как бы правдоподобно они ни выглядели.
- Защитная рамка периметра ([§4](#4-обнаружение-целей-и-защитные-рамки)) ограничивает, куда может вести объявленная цель (та же частная сеть `/24`, если явно не настроено иное), а подтверждение пользователя решает, будет ли она вообще просканирована, — ложная цель за пределами периметра даже не предлагается; цель внутри периметра по-прежнему требует явного подтверждения перед любым сканированием.

## 11. Совместимость с терминалами

TUI (Textual) автоматически определяет возможности терминала (эмулятор, размер) и соответственно подстраивает свою структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`), без ручных параметров. Режим CLI всегда остаётся простым текстом, независимо от терминала. Это правило общее для всего набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по определённому эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| TTY Linux, старый SSH | `mono` |
| Нераспознанный эмулятор | `reduced` (запасной вариант по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Верхний предел профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **более строгий из двух** (эмулятор и размер): Ghostty на весь экран, уменьшенный до 70 столбцов, опускается до `mono`, хотя его эмулятор позволил бы `complete`. Обновляется на лету клавишей `r`.

## 12. Экспорт

Текстовые и HTML-отчёты пишутся на языке, выбранном в Настройках («Язык экспорта», по умолчанию — язык интерфейса); JSON остаётся данными и не переводится. По умолчанию отчёты создаются в `var/exports/` (рабочий путь привязан к папке проекта, `$OMEGA_DEEP_VAR_DIR` позволяет его переопределить) или по указанному пути (`--output` в CLI, диалоговое окно в TUI). Понятное имя файла с отметкой времени: `analyse-{профиль}-{дата}.ext`, `analyse-custom-{дата}.ext` для личного профиля.

### JSON — источник истины

Полная структура анализа (`Scan` + `Host[]` + `ArchitectureGraph`), строго сериализуемая в JSON, включая уровни доверия.

### Текст — компактный отчёт для чтения

Читается вне терминала, без кодов ANSI, — граф в виде списка рёбер.

### HTML — самостоятельный веб-отчёт

5 тем на выбор (`--theme` в CLI, переключатель в TUI; по умолчанию следует активной теме интерфейса, если есть соответствие). Собственная вёрстка: контейнер, сетка сведений, блоки статистики по состоянию портов, цветные значки, **SVG-диаграмма графа архитектуры** (см. [§8](#8-граф-архитектуры)) — то же визуальное семейство, что у `omega-scan`/`omega-check`.

## 13. История и сравнение

Каждый анализ сохраняется (SQLite, `var/db/omega-deep.db`): один `scan_id` охватывает корневую цель **и** все обнаруженные/принятые хосты, а также восстановленный граф. История по корневой цели (с отдельным столбцом для числа обнаруженных целей), подробности прошлого анализа (хосты + граф), сравнение двух анализов (состояние портов только **корневой цели** — сравнение графов обнаружения было бы возможным расширением, пока ненужным) и повтор анализа той же корневой цели без повторного ввода.

## 15. Вне рамок

- Сканирование CVE
- Активное обнаружение SQLi, XSS, RCE
- Определение операционной системы
- Низкоуровневые техники сканирования в духе nmap (SYN-сканирование, сырые пакеты)
- Обход сайтов (crawling)
- Фаззинг
- Перебор
- Сканирование обнаруженной цели без явного подтверждения — никогда, ни в каком режиме
- Обнаружение за пределами частной подсети исходной цели без явной настройки
- Веб-панель
